# PR 范围与验收规范

[English](pr-policy.md) | [简体中文](pr-policy.zh-CN.md)

PanWatch 的维护者验收精力有限。每个贡献应完成一个可独立使用的行为，并提供可复核的验收材料。实现已经完成，不代表产品范围一定会接收。

## 先确定产品范围

新增市场、认证模式、外部账户同步、新依赖和架构调整，开发前先通过 Issue 讨论用户问题、最小可用版本、默认行为、兼容性、支持能力和持续维护责任。方案得到认可之后，具体实现仍需评审。

独立功能与无关清理分开提交；每个小 PR 合入后都必须可用。不能为了过行数门槛，把不可用的半套功能切成几个必须一起合入的 PR。有独立验收价值的公共基础可以先交付。新市场和连接器默认关闭，高级能力逐项评估。

## 改动规模门槛

初始自动门槛为 **20 个生产文件、800 行生产代码新增加删除**，两项都需满足。测试、Markdown 文档和已知 lockfile 不计入这个门槛，但仍属于评审范围；工作流、运行配置和翻译计入。把生产文件重命名到排除目录也不会消除原来的计数。

超过门槛时，拆成可独立交付的版本，或由维护者明确批准范围例外。规模门槛用于控制验收负担，小于门槛也不代表功能聚焦或实现正确。数值保存在 `.github/pr-policy.json`，可以根据首轮执行情况调整。

维护者添加 `pr:scope-approved`，可为当前 head 批准有必要的跨模块改动。新推送后例外失效，需重新审阅再添加。例外只豁免规模，不豁免验收材料、正确性或明确的拆分要求。

## 验收报告

使用仓库 PR 模板，正文以英文填写 `Background`、`Changes`、`Scope`、`Validation`、`Acceptance evidence`、`Boundaries and risks`、`Follow-up`。讨论可使用中文或英文；英文标题采用 `type(scope): subject`。Follow-up 无后续事项时可以填写 None。

Validation 填写 `Tested commit:`，指向当前 head 的7–40位哈希，并填写 `Commands and results:`。新推送后执行与改动相关的检查并更新报告，不要把未执行命令或作者声明写成已独立验证的结果。

Acceptance evidence 包含 `Steps:`、`Expected:`、`Observed:`、`Evidence:`。提供 GitHub 工作流/日志、脱敏截图或录屏链接，或者直接贴简洁的脱敏输出。材料应能从 PR 访问，本地文件路径不能当成交付报告。不适用的检查需解释原因；注释、空勾选框、TODO、单独的 N/A 或 None 不算证据。机器人只能核对材料是否填写并关联当前提交，无法证明声明真实。

按实际风险提供证据：

| 改动 | 相关证据 |
| --- | --- |
| 小范围修复 | 前后复现与相关检查 |
| UI 行为 | 相关测试与截图；涉及布局时覆盖明暗主题、桌面和手机 |
| 代理/认证 | 真实部署与会话流程、信任边界、登录退出、既有访问方式兼容 |
| 新市场 | 开关流程、小量真实行情样本、标的/币种/时间校验、成熟市场兼容 |
| 持仓导入/同步 | 预览和应用结果、字段归属、失败保留、未支持记录与币种处理 |
| 文档/工具 | 对应预览或工具检查；说明为何无需业务测试或 UI 验收 |

每个 PR 不必都跑完整项目测试或提交浏览器报告，检查范围与变更匹配即可。材料必须移除个人持仓、密钥与凭据。

## 自动提示与关闭

工作流初始为 **audit 只读模式**：只读取元数据和文件、输出检查结果，不写标签、评论或状态，不关闭 PR。由维护者单独启用 enforce。

**enforce 模式**下：

1. PR 有变化时及每日巡检，核对当前提交、报告结构与规模。
2. 维护一条列出整改项的提示，添加 `pr:needs-work`，在 PR head 上报告 `PR policy` 状态。
3. 从**首次提示起给14天**，第7天单独发提醒，逾期仍不符合时在每日巡检关闭。评论、推送不自动顺延；达到要求后清除计时，重新打开后给予新窗口。
4. 关闭前重新检查 head、正文和标签，避免按旧快照关闭。接口失败或文件列表不完整时不执行关闭判断。

已有 PR 同样从新提示开始获得完整宽限期，不按旧创建日期直接关闭。Draft 也会收到提示；长期规划放在 Issue，有明确用途的未完成 Draft 可以申请 hold。关闭保留分支，作者修正后可以重开或重新提交拆分版本。

已达到规范、等待维护者评审的 PR 不会因维护者忙而自动关闭。CI 待批准、基础设施不可用、无关的基线失败本身不触发关闭；报告需要说明限制，它们仍可能阻止合入。规范检查通过后仍需人工判断产品价值、证据质量和代码正确性。

维护者标签：

| 标签 | 作用 |
| --- | --- |
| `pr:needs-work` | 机器人维护的未达标标记 |
| `pr:needs-split` | 人工认定需要收窄；维护者移除前阻止验收通过 |
| `pr:needs-evidence` | 人工认定证据不足；移除前阻止通过 |
| `pr:scope-approved` | 当前已审阅 head 的规模例外，不豁免证据 |
| `pr:hold` | 暂停自动关闭、清除截止时间，合入状态保持 pending；移除后若仍未达标，重新给宽限期 |

作者补齐人工要求后应申请复审；复审等待期间维护者可以用 hold 暂停。未移除的人工阻塞标签仍视为尚未达标。

## 启用顺序

1. 合入规范 PR，保持 `PR_POLICY_MODE` 未设置，先做只读演练，查看手动工作流结果并调整门槛。
2. 向当前贡献者逐项反馈过渡要求；已讨论的大 PR 说明接受的最小范围，避免只给泛泛拒绝。
3. 设置仓库 Actions variable `PR_POLICY_MODE=enforce`，手动运行 **PR contribution policy**。工作流会创建所需的5个标签、发初次提示并开始新计时。
4. 确认真实 PR 上状态正确后，将 **PR policy** 设为 main 的必过检查；保留已有必过检查。未配置分支保护或 ruleset 时，机器人只报告失败，不能阻止维护者合并。
5. 确认 Actions event policy 允许此元数据专用 `pull_request_target` 工作流；GitHub 默认策略可能拦截，启用时需核对仓库设置。

有写权限的工作流只执行默认分支中的可信规则代码，不 checkout 贡献者 head 或执行其报告命令。回归测试使用独立只读工作流。GitHub 定时任务可能延迟，关闭发生在到期后的首次成功巡检，并非精确到秒。

GitHub 官方说明：[可信事件处理](https://docs.github.com/en/actions/reference/security/securely-using-pull_request_target)、[提交状态](https://docs.github.com/en/rest/commits/statuses)、[必过检查](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets)。
